# План реализации и статус

DEX-арбитражный бот: ядро на C++ (hot path), аналитика на Java (cold path),
контракт-исполнитель на Solidity. Один проект закрывает два курса, поэтому у каждой
части своя содержательная логика.

## Архитектура

```
   Arbitrum: RPC (HTTP) / WebSocket
            │  newHeads, logs (Swap/Mint/Burn)
            ▼
┌──────────────────── C++ core — hot path ────────────────────┐
│ feed ─▶ локальная копия пулов (тики, ликвидность) ─▶        │
│ стратегия: оптимальный объём, точная прибыль ─▶             │
│ исполнитель (свой поток): eth_call ─▶ подпись ─▶ отправка   │──▶ ArbExecutor.sol
└──────┬──────────────────────────────────────────────────────┘      (флеш-своп A→B)
       │ JSON-события через ZeroMQ PUB (неблокирующая очередь)
       ▼
┌──────────────────── Java analytics — cold path ─────────────┐
│ приём событий ─▶ PostgreSQL ─▶ REST ─▶ дашборд              │
│ web3j: поиск пулов ─▶ конфиг для бота; история ─▶ бэктест   │
└─────────────────────────────────────────────────────────────┘
```

**Правило №1:** C++ никогда не ждёт Java. События уходят через ограниченную очередь;
если Java лежит или тормозит, события отбрасываются, бот работает дальше.

## Этапы

Легенда: ✅ готово и проверено · ⬜ не делалось

### ✅ Этап 0: Инфраструктура
Структура репо, CMake-пресеты (debug с ASan/UBSan, release), Gradle, docker-compose.

### ✅ Этап 1: Ethereum-примитивы (`core/src/eth/`)
hex, u256, Keccak-256, адреса с EIP-55, ABI-кодер/декодер (включая динамические типы
и массивы кортежей), парсер ABI JSON (функции, события, custom errors), RLP.
**Проверка:** все тесты совпадают с `cast keccak / sig / abi-encode / to-rlp`.

### ✅ Этап 2: RPC и чтение пулов (`net/`, `dex/`)
HTTP JSON-RPC с batch-запросами и повторами, WebSocket `eth_subscribe`, опрос по HTTP
для публичного RPC. Пулы находятся через `factory.getPool`, состояние читается батчами.
ABI берутся из `core/abi/*.json`, их экспортирует `forge inspect`.
**Проверка:** бот на mainnet находит 20 пулов в 5 парах и печатает цены каждый блок.

### ✅ Этап 3: Связка с Java
Отправка JSON-событий из C++ (ZeroMQ, отдельный поток), приём в Java (JeroMQ),
таблицы Flyway, REST, дашборд с графиком цен по пулам.
**Проверка:** сквозной прогон бот → Java: 49 событий, 0 отклонено; тест Java через
настоящий ZeroMQ-сокет.

### ✅ Этап 4: Локальная математика V3 (`dex/v3_math`, `dex/v3_pool`)
Порт `FullMath`, `TickMath`, `SqrtPriceMath`, `SwapMath`, `LiquidityMath`; симуляция
свопа с переходом через тики пословно, как в `TickBitmap`; тики загружаются через
TickLens и обновляются по событиям Mint/Burn.
**Проверка:** `hft_verify` — **305 из 305** котировок совпали с QuoterV2 **до wei**;
офлайн-фикстура из 3 реальных пулов в юнит-тестах; 20 констант TickMath сверены с
расчётом на Python до 128-битной точности.

### ✅ Этап 5: Стратегия (`strategy/two_pool_arb`)
Циклы из двух пулов одной пары в обе стороны. Быстрый фильтр по предельному курсу;
начальное приближение — точная формула для двух пулов x·y=k по виртуальным резервам;
уточнение золотым сечением по точным котировкам с переходами через тики; газ и
минимальная прибыль в WETH. Расчёт делается на границе транзакции (не между двумя
Swap-логами одной транзакции).
**Проверка:** тесты против полного перебора и формулы; бенчмарки: котировка в одном
тике 1.3 мкс, через 20 тиков 18.6 мкс, полное решение по паре ~260 мкс.

### ✅ Этап 6: Контракт-исполнитель (`contracts/src/ArbExecutor.sol`)
Флеш-своп: пул A отдаёт токен первым, в колбэке он продаётся в пуле B, пулу A
возвращается долг; проверка `minProfit`, защита колбэка, `onlyOwner`, вывод средств.
**Проверка:** 7 тестов Foundry на форке Arbitrum; после того как «кит» продаёт 300 WETH,
цикл на 20 WETH приносит ~0.86 WETH.

### ✅ Этап 7: Транзакции и подпись (`eth/tx`, `eth/signer`, `exec/executor`)
EIP-1559, RLP, libsecp256k1, локальный nonce, отдельный поток исполнителя, ожидание
чека, фактическая прибыль из события `Arbitrage`.
**Проверка:** подписанные транзакции совпадают с `cast mktx` байт в байт; подпись
занимает ~30 мкс.

### ✅ Этап 8: Симуляция перед отправкой
`eth_call` той же транзакции; при откате — не отправлять, причина декодируется по ABI
(например, `InsufficientProfit`).

### ✅ Этап 9: Демо на форке (`scripts/demo_fork.sh`)
anvil-форк → деплой → бот → кит продаёт 300 WETH → бот находит, симулирует,
подписывает, отправляет → прибыль.
**Проверка:** ожидаемая прибыль +3.173185 WETH, фактическая 3.173185067 WETH;
решение 3.7 мс, подпись 32 мкс, отправка 1.2 мс; сделка видна в Java (PnL, газ, статус).

### ✅ Этап 10: Продвинутая Java
Поиск пулов через web3j (134 пула между 9 токенами), генерация конфига для бота
(бот его принимает: 32 пула в 8 парах), индексация истории свопов (`eth_getLogs`,
JDBC-батчи, учёт непрерывных диапазонов), бэктестер, PnL-кривая, гистограмма задержек.

Бэктестер оценивает рынок на конец каждого блока (внутриблочные расхождения забирают
боты у секвенсора) формулой для двух пулов x·y=k, ограничивая объём текущим интервалом
тиков, где ликвидность гарантированно не меняется.
**Проверка:** час mainnet = 19 710 свопов, 13 возможностей на 0.000876 WETH; шесть лучших
перепроверены точными котировками QuoterV2 на тех же блоках — все реально прибыльны,
расхождение с бэктестом до ~2.5%.

**Чему научила проверка.** Первая версия бэктеста показывала сотни «возможностей» на
1.9 WETH. Точные котировки их опровергли, а разбор нашёл две ошибки: оценку посреди
блока и прогон через пропуск в истории (цена пула «застывала» на старом значении).
Обе исправлены, бэктест через пропуск теперь отказывается считать.

### ⬜ Этап 11 (опционально)
Треугольный арбитраж, другие DEX (Camelot, Sushi V3), вторая сеть (Base), lock-free
очереди, свой uint256 на 4×64 бита вместо Boost (котировки станут в разы быстрее),
приватный RPC рядом с секвенсором.

## Чему научил mainnet

На реальном Arbitrum валовые расхождения между пулами есть постоянно, но почти всегда
меньше газа: их закрывают профессиональные боты с инфраструктурой рядом с секвенсором.
Поэтому исполнение по умолчанию выключено, а прибыльный сценарий показывается на форке.
